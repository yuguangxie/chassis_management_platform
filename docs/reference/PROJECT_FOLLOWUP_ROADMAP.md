# 项目后续五阶段工作安排

## 1. 规划依据

本安排基于 `docs/audit/` 中 2026-07-10 的工程审计结果：

- 总体评分：48/100。
- UI 平均还原度：87/100。
- 加权功能完成度：46.1%。
- 真实功能实现率：15.5%。
- 问题总数：P0 5 项、P1 12 项、P2 19 项、P3 6 项。
- 当前就绪等级：`NOT_READY`。

主要依据文件：

- `docs/audit/00_EXECUTIVE_SUMMARY.md`
- `docs/audit/14_ISSUE_REGISTER.md`
- `docs/audit/15_REMEDIATION_PLAN.md`
- `docs/audit/audit_results.json`

本规划把审计整改计划合并为 5 个可独立实施、可独立验收的小阶段。阶段必须按顺序执行，前一阶段的门禁未通过时，不得宣称后一阶段完成，也不得连接真实车辆。

## 2. 总体原则

1. 安全优先于 UI 和交付速度。
2. Mock、fallback、Stub 不得计为真实功能完成。
3. 每个“通过”结论必须有自动化测试、接口响应、日志或截图证据。
4. 原始 `docs/audit/evidence/` 作为历史基线，不得覆盖或删除。
5. 每阶段新证据写入 `docs/verification/phase-0X/`。
6. 生产模式必须明确区分真实硬件、Mock 和离线 fallback。
7. 所有车辆运动控制必须经过后端 `SafetyInterlockService`，UI 不得直接发 CAN。
8. `0x123`、`0x126`、CANopen NMT、PID 调试始终默认关闭。

## 4. 阶段一：安全控制与可信边界

### 4.1 目标

关闭全部 P0，确保控制操作可被可靠中止、急停能真正停车、断链时保守失败、UI 展示的联锁和待发报文与后端实际行为一致，并建立不可伪造的身份边界。

### 4.2 工作范围

- 重构 EOL 会话 task 生命周期：暂停、继续、中止、急停必须在步骤边界生效。
- 急停使用高优先级停车路径，周期发送零速/制动指令，直到反馈确认或安全超时。
- 安全停车实现状态机，不再只发送一次报文。
- 使用接收时刻而非处理时刻计算关键帧在线状态。
- CAN 接收改为有界队列，过期帧不得维持“在线”。
- `GET /control/status` 和 `GET /control/interlock-status` 直接返回真实联锁结果。
- 0x121 预览只使用同一个权威编码结果，UI Byte0~Byte7 必须与实际发帧相同。
- 实现服务端认证和 RBAC；删除 `state.current_role = admin` 和客户端自报角色信任。
- 删除报告、维护模式、危险配置和控制接口必须使用服务端身份。
- 建立显式 `dev/mock/production` 配置，开发仿真不得向 [REDACTED_CAN1_GATEWAY]/99 发包。
- UDP 按 datagram 校验 `13*n`，禁止半包跨数据报拼接。

### 4.3 交付物

- 可取消的 EOL task/state machine 基础设施。
- 可靠急停与安全停车服务。
- 统一联锁状态 DTO 和 0x121 权威预览 DTO。
- 本地可信认证/RBAC 最小闭环。
- 开发、Mock、生产三套明确配置及启动脚本。
- 安全、越权、断链、协议边界测试。
- `docs/verification/phase-01/` 证据包。

### 4.4 验收门禁

1. pause 后步骤数保持不变；resume 后才继续。
2. abort 后状态保持 `ABORTED`，后台任务不可覆盖。
3. emergency-stop 后不再执行后续步骤，并确认停车反馈；超时必须维持锁存并报警。
4. CAN1/CAN2 均断开时不能开始 EOL，控制接口返回结构化 409。
5. 停止 simulator 后 2 秒内通道离线，5 秒时控制仍必须被拒绝。
6. UI 预览 bytes 与 simulator 实收 bytes 完全一致。
7. 未认证请求不能进入维护模式、控制车辆或删除报告。
8. 伪造 `role`、`x-role`、用户字段无效。
9. UDP 截断报文不能与下一数据报拼成合法帧。
10. P0 必须全部关闭并有失败路径测试；本阶段仍禁止真实车辆。

### 4.5 非目标

- 不在本阶段重做 11 页 UI。
- 不在本阶段实现完整报告模板和历史下载。
- 不以“按钮返回 200”作为安全功能完成。

## 5. 阶段二：真实 EOL 与全链路持久化

### 5.1 目标

把当前步骤播放器改造成由 `configs/test_plan.yaml` 驱动的真实检测引擎，并使会话、步骤、断言、原始帧、解码信号、告警和报告记录形成可恢复、可追溯的数据闭环。

### 5.2 工作范围

- 定义并校验测试计划 Pydantic 模型。
- 12 步均实现明确的进入条件、动作、采样窗口、断言、超时和失败策略。
- 阈值来自配置，不允许写死在 dashboard 或 engine。
- 转向无响应、制动失败、低 SOC、严重告警、CAN 断开、DBC 未加载、数据库不可写必须正确 FAIL。
- 人工步骤支持等待、确认、超时、中止和审计。
- 限制同工位并发会话，明确排队或拒绝策略。
- 建立 session Unit of Work 和数据库 transaction。
- 批量持久化 `test_sessions`、`test_steps`、`test_assertions`、`raw_can_frames`、`decoded_signals`、`alarms`、`reports`。
- 实现 `SignalLogWriter`，保留信号质量、来源帧和 session_id。
- 0x102 按 override 展开真实 unsigned bool 和 bitmap 信号。
- 支持进程重启后的未完成会话恢复或明确安全终止。

### 5.3 交付物

- YAML 驱动 EOL engine。
- 真实断言执行器和步骤日志。
- 数据库 repository、事务和恢复机制。
- 解码信号与告警持久化。
- 五个既有 profile 加扩展故障 profile 的回归测试。
- `docs/verification/phase-02/` 证据包。

### 5.4 验收门禁

1. `normal_pass` 为 PASS 且执行 12 步。
2. `bms_low_soc` 在 BMS 步骤 FAIL。
3. `warning_fault` 在正确告警步骤 FAIL，并按策略触发安全停车。
4. `steering_no_response` 和 `brake_fail` 必须 FAIL。
5. CAN 断开、DBC 未加载、数据库不可写均不得生成 PASS。
6. 用户中止、急停、进程重启和重复执行结果稳定。
7. 禁止两个运动检测会话同时运行。
8. 每次会话在所有核心表中有可关联记录，事务失败时不留下半会话。
9. EOL dashboard、WebSocket 和数据库状态一致。

### 5.5 非目标

- 本阶段优先确保检测结论正确，不做像素级 UI 调整。
- 不接真实车辆；仅使用 Mock、仿真器和隔离回环测试。

## 6. 阶段三：真实业务数据、API 与报告

### 6.1 目标

让总览、监控、仪表盘、曲线、告警、报告、历史和系统设置使用可追溯的真实数据，替换生产路径中的无标识 Mock/Stub，并统一 API、错误、下载和报告契约。

### 6.2 工作范围

- 所有 dashboard 返回 `data_source`、`mock`、`quality`、`updated_at`。
- 生产模式禁止静默 fallback；离线和 Mock 必须明确标记。
- 统一 request/response Pydantic 模型、错误结构、trace_id 和 OpenAPI 契约。
- TCP：实现真实 `TcpCanGateway`，或从配置/API/UI 中明确移除为“未支持”。
- CAN 详情使用当前实际帧和 DBC 解码，不返回固定 0x77/0x121 信号值。
- CAN 统计、信号趋势、Watchlist、曲线和告警历史读取真实数据。
- 报告列表、扫描、关联数据和历史页面读取数据库与受控文件目录。
- 生成完整 JSON、DOCX、PDF、CSV；包含版本、DBC hash、配置 hash、计划、步骤、断言、操作员和结论。
- 修复中文字体和编码，PDF/DOCX 必须可读。
- 预览真实 PDF/DOCX/JSON/CSV，不使用固定白纸模板。
- 实现安全导出、下载、重新生成、打印队列、目录打开和历史回放元数据。
- 报告删除使用服务端 RBAC，不存在 ID 返回 404。

### 6.3 交付物

- 统一 API model 和错误中间件。
- 真实 dashboard/query/statistics 服务。
- 报告模板、字体资源、生成与预览服务。
- 历史、下载、导出和关联数据服务。
- API 契约测试、报告渲染测试和权限测试。
- `docs/verification/phase-03/` 证据包。

### 6.4 验收门禁

1. 核心业务页面的生产响应不含未说明的固定 Mock 数据。
2. 所有 4xx/5xx 统一包含 `code/message/details/trace_id`。
3. OpenAPI contract test 可检测请求或响应漂移。
4. PASS 与 FAIL 报告中文可读、内容完整、数据库记录可关联。
5. 预览内容与磁盘真实文件一致。
6. 历史筛选、分页、时间线、日志、下载、回放和报告跳转均使用真实会话。
7. 删除、维护、导出和文件访问通过 RBAC 与路径安全测试。
8. 目标生产流程中不再存在“接口已预留”的 Stub。

### 6.5 非目标

- 不在本阶段进行安装包和 24 小时台架验收。
- UI 仅适配新数据契约，像素和性能收口放在阶段四。

## 7. 阶段四：实时性能、可靠性与 UI 收口

### 7.1 目标

使系统在持续 CAN 高负载下保持正确时效、受控资源和可靠重连，同时完成 11 页响应式、状态一致性和视觉细节收口。

### 7.2 工作范围

- CAN 收帧使用有界队列、批处理和明确丢弃/降级策略。
- WebSocket 按规范节流：信号约 10Hz、统计约 1Hz，原始帧按订阅按需推送。
- 前端直接消费 WebSocket payload，禁止每帧再触发 HTTP 请求。
- WsClient 实现单例状态机、重连、退避、subscribe/unsubscribe/off 和销毁。
- 原始 CAN 与信号日志采用异步批量写、按会话/大小轮转、压缩和保留策略。
- fps 改为滚动窗口；recent buffer 按通道配置，满足容量要求。
- 路由懒加载并拆分 ECharts/vendor bundle。
- TopStatusBar 使用唯一真实状态源。
- 实时曲线勾选实际控制 series。
- ECharts 使用 ResizeObserver，消除零尺寸初始化警告。
- 修复白底原生控件。
- 11 页在 1920x1080 一屏显示；1366x768 保持核心操作可见，仅局部滚动。
- 重新生成 UI 截图、差异图和运行指标。

### 7.3 交付物

- 有界 CAN pipeline 和 WebSocket cadence。
- 日志轮转、空间告警和清理策略。
- 前端连接生命周期和 ECharts resize 基础设施。
- 11 页双分辨率截图和 Playwright/Electron UI 测试。
- 1000fps 性能报告。
- `docs/verification/phase-04/` 证据包。

### 7.4 验收门禁

1. 1000fps 持续 10 分钟，无持续 backlog、未处理任务无界增长或日志失控。
2. simulator 停止后 2 秒内通道离线，积压帧不得刷新在线状态。
3. WebSocket topic 频率符合配置，慢客户端不阻塞 CAN 接收。
4. 10 分钟页面切换后无重复连接、重复 handler 或明显内存增长。
5. 原始日志轮转、保留和磁盘阈值可验证。
6. 1920x1080 无页面级滚动条；1366x768 所有安全按钮和状态可操作。
7. 无大红 Failed to fetch、白底控件、空图或状态矛盾。
8. 前端主 bundle 不再触发当前 1.39MB 单块警告，或有书面、可测的例外说明。

### 7.5 非目标

- 不在性能整改中绕过安全检查换取吞吐。
- 不因视觉接近参考图而隐藏真实离线、Mock 或错误状态。

## 8. 阶段五：测试体系、打包部署与试点验收

### 8.1 目标

建立可重复 CI 和生产构建，使 Electron 能在干净 Windows 工控机离线安装、拉起并监管 FastAPI，完成升级、崩溃恢复和封闭台架验收。

### 8.2 工作范围

- 修复根目录后端/仿真器测试命令和 Python 包安装方式。
- 增加 pytest coverage、Vitest、ESLint、Playwright/Electron E2E。
- 为控制、EOL、安全、协议、数据库和报告设置覆盖率门禁。
- 升级 Electron、Vite、ECharts 等高/中危依赖并回归。
- 使用 electron-builder 或等价方案生成 Windows 安装包。
- 生产模式 `loadFile(dist/index.html)`，开发模式才连接 Vite。
- 打包或安装后端 Python runtime；Electron 负责启动、健康等待、退出和崩溃重启。
- 配置、DBC、数据库、日志和报告目录使用明确的可写生产路径。
- 实现首次初始化、端口冲突提示、防火墙说明、自动启动、升级和回滚。
- 在干净 Windows 环境执行离线安装和升级测试。
- 在独立批准的封闭台架执行 24 小时 soak、断链、断电、后端崩溃、仿真器重启、数据库失败和急停测试。
- 完成一次独立复审，重新计算生产就绪等级。

### 8.3 交付物

- CI pipeline 与覆盖率报告。
- 可签名 Windows 安装包和校验值。
- 后端进程监管和生产配置。
- 安装、升级、回滚、运维和故障恢复文档。
- 干净机安装证据与 24 小时封闭台架报告。
- 最终复审和试点准入清单。
- `docs/verification/phase-05/` 证据包。

### 8.4 验收门禁

1. 从项目根目录一条命令执行后端、仿真器和前端测试。
2. 核心控制、EOL 和安全模块分支覆盖达到项目批准门槛，失败路径全部覆盖。
3. `npm audit` 无未接受的 high/critical。
4. 安装包在无 Node、无开发 Vite、无系统 Python 的干净 Windows 机器启动。
5. Electron 能拉起后端、等待健康、展示启动失败原因并在退出时清理进程。
6. 应用离线重启后配置、会话和历史数据保持一致。
7. 24 小时 soak 无内存、句柄、socket、数据库或磁盘失控。
8. 所有 P0/P1 关闭，剩余问题有正式风险接受记录。
9. 独立复审至少达到 `PILOT_READY`，方可进入有限试点。
10. `PILOT_READY` 不等于允许连接真实车辆，仍需项目安全负责人书面批准。

## 9. 阶段执行与记录规则

每阶段开始前：

1. 固化当前代码版本或提交哈希。
2. 从 `issue_register.csv` 提取本阶段问题。
3. 建立 `docs/verification/phase-0X/`，记录环境、命令和基线。

每阶段结束时必须输出：

- 修改文件清单。
- 问题关闭与遗留表。
- 测试命令和原始结果。
- API、日志、数据库和截图证据。
- 安全回归结论。
- 下一阶段是否允许启动的明确门禁结论。

如果验收失败，阶段状态必须保持“未完成”，不得用 Mock、Stub 或手工修改结果绕过。
